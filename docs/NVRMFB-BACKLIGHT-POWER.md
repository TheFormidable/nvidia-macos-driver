# NVRMFB backlight power requests

How NVRMFB handles the brightness of a laptop panel wired to the NVIDIA GPU (a panel on the integrated GPU is
[HYBRID-LAPTOPS.md](HYBRID-LAPTOPS.md)'s). It is the original project's work: pull request 312 and the ones after it by
Ersiter, and the brightness kept on disk of its #582, which this fork took in 3.0.18. It is on by default. This fork's
only test machine is a desktop without an internal panel, so at 3.0.20 none of it has run here.

`linear-brightness` and `brightness` requests from the display slider update the user target immediately. After NVKMS applies a user request successfully, a separate low-priority callback saves the latest applied target only after two seconds without another user request. Hardware updates are not delayed. Temporary power requests and conversion probes do not restart this idle interval. A failed save is retried after two seconds without requiring another brightness event; a newer user target supersedes the old one and gets its own idle interval. Handler teardown cancels and drains the hardware callback before the save callback.

The `/options` property `nullmoth-backlight` stores three bytes: version 2 followed by the little-endian 16-bit logical target over the usable 5..100% hardware span. Legacy one-byte hardware percentages and version-1 targets remain readable: they are converted to the new range while retaining their previous rounded, floor-protected hardware output. An unchanged saved target is not written again. Older driver versions cannot interpret version-2 records. Uninstall removes this driver-owned NVRAM variable. On the next handler creation, NVRMFB reads a valid value, initializes the display parameters to it, and queues an asynchronous restore. A missing or invalid value falls back to the hardware's initial level. Every display rebind publishes the user target, even when a temporary power request last dimmed the panel. Whole-display power requests do not replace the user target; temporary dimming is not saved. A restart or teardown before the idle interval completes may retain the previous saved target.

Run `python3 tools/check_nvrmfb_backlight_target.py` for request routing and `python3 tools/test_nvrmfb_backlight_persistence.py` for extracted `withRM`, `setDisplay`, `applyFire`, and `persistFire` behavior. These checks use fixtures and do not build the kext or verify that `/options` survives a physical restart. On Linux at 3.0.20 the second passes; the first is not part of `tools/run_all_tests.py` and no longer compiles, because its fixture predates fields the handler has gained since (`fUserSeen`, and the keeper's `gBacklightLock`). Hardware evidence is the original's: on an RTX 5080 Laptop with macOS 26.7 the pull request's author confirmed that the slider spans hardware 5..100% and that the saved brightness target restores after restart. Keyboard event handling remains with macOS.

## Parameter precision and backend limits

The four IODisplay brightness and conversion-probe parameters advertise a logical range of 0–65535. IOKit normalizes its float API using each parameter's advertised min/max; 65535 is this driver's precision choice, not an Apple-mandated range or an additional hardware capability. Both real parameter values stay synchronized after a user request. Temporary power requests do not overwrite either user value, and conversion probes only update the opposite probe.

The logical target remains unquantized through probes, pending requests and version-2 restart persistence. The final NVKMS call uses `5 + round(level * 95 / 65535)`: slider zero maps to hardware 5%, and slider maximum maps to 100%. Hardware initialization uses the inverse mapping, with hardware values at or below 5% mapping to logical zero. The 5% floor protects panels that turn completely off at zero; the affine mapping removes the old bottom 5% plateau while retaining integer-percent hardware quantization. This is a usable-range mapping, not a perceptual curve. AppleBacklightDisplay's public source uses 0..255 as its default power-brightness span when the display publishes no power-state range; that full-power request restores the saved logical target. Keyboard stepping and system volume handling are unchanged.

Public contracts: [Apple IODisplay float normalization](https://github.com/apple-oss-distributions/IOKitUser/blob/main/graphics.subproj/IODisplayLib.c), [IODisplay parameter handling](https://github.com/apple-oss-distributions/IOGraphics/blob/main/IOGraphicsFamily/IODisplay.cpp), and [NVIDIA integer-percent backlight](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/main/kernel-open/nvidia-modeset/nvidia-modeset-linux.c).

A panel for which NVKMS registers no backlight is driven over its eDP AUX channel when its DPCD (0x701, 0x702) says it takes brightness there (since the original's 2.9; boot argument `nvfbedpbl=0` turns this off). A panel that only has the PWM pin then has no brightness control, and the kernel log says so.

## Firmware that drops NVRAM writes

Since 3.0.18 (the original project's #582). Some OpenCore setups (`DisableVariableWrite` without emulated NVRAM) never store runtime NVRAM writes, so `nullmoth-backlight` comes back at every restart with an old value. The installer adds a launch daemon, `com.nullmoth.backlight` (`/Library/NullMoth/backlight.sh`), that copies the variable to `/Library/NullMoth/backlight.level` every 30 seconds and at shutdown. At start it waits for the internal panel's brightness control (up to two minutes) and, only when the variable disagrees with its copy, writes the copied level to the root-only sysctl `debug.nvrmfb_backlight_restore`. Where NVRAM keeps writes, the two agree and the daemon does nothing. NVRMFB accepts the restore only while the user has not moved the brightness this boot; a request for exactly the maximum does not count as moving it, because the display stack sends one at every start. Restores and refusals are logged to `/Library/NullMoth/backlight.log` (last 200 lines). On a machine without an internal panel the sysctl answers nothing and the daemon ends after its two minutes. Uninstall removes the daemon, its copy and its log, and the NVRAM variable; to stop it by hand, `sudo launchctl bootout system/com.nullmoth.backlight`. Tests: `python3 tools/test_backlight_keeper.py` (the daemon against stub `nvram`/`sysctl`, and the kernel's restore rule; the daemon calls macOS's `base64 -D`, so on Linux 3 of its arms fail, on the original's own tree as well) and `python3 tools/test_nvrmfb_backlight_persistence.py`. No run on a panel is recorded in this fork.
