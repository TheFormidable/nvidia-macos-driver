# Two-plane IOSurfaces in VRAM (#475) and deferred surface uploads (#476)

#475 is implemented in this release and on by default; #476 is not implemented. Both alter the ordering and lifetime
rules of the surface paths, and a host test can only model a table, not the ordering. This note records how #475 was
done and what only a card can show about it, what #476 would need, and the runs that decide them. It also lists the
related opt-in pieces a test session can flip.

## Related pieces already in the tree (off by default)

| Switch | What it does |
|---|---|
| `NVMTL_SURF_IMPORT_CACHE=1` | wrappers of one single-plane surface share one import of its family VRAM, kept 2 s after the last wrapper |
| `NVMTL_PLANE_SEED=1` | a seed gap caused only by our own surface-outs of other planes does not force an upload |
| `NVMTL_HOST_PAGES_SHARE=1` | wrappers of one surface share one import of its pages for the host copies |
| `NVMTL_FC_SPEC=1` | one module per function for every function-constant set |

The page-off wait without the accelerator lock, which both changes need, is no longer in this list: it is on by
default (`sysctl debug.nvaccel_pageoff_unlocked_wait` reads 1) and `nvaccel_pageoff_locked=1` is its only way back.

## #475: each plane of a two-plane surface in its own VRAM

### What changed
Until 2.9 only a single-plane surface could be backed by imported family VRAM. A two-plane surface (NV12 capture and
video frames) kept one private image per plane, uploaded from the CPU pages before it was drawn over and copied out
after. Now each plane of such a surface can be drawn straight into VRAM of its own.

### The mechanism chosen
Each plane of a two-plane surface is backed by the family's own device cache for that plane, as plane 0 of a
single-plane surface always was: one resource and one VRAM allocation per plane, holding that plane from offset 0. The
plugin names the plane's byte range in the surface's memory when it asks for the VRAM (escape 0xE2 with plane flag
0x20000000; size = offset << 32 | length). The kernel checks the range against the surface and the VRAM, refuses a
plane that shares its resource or VRAM with plane 0, or its validity words (one set of words for both planes would let
one plane's page-off mark the other current), records the range together with the surface it was given for (a
page-off of the resource while it belongs to another surface copies nothing) and the one validity bit the resource
uses, and from then on pages that plane off into that range only: the copy engine fills a staging buffer and the CPU
writes it at the plane's offset. A plane's page-off never falls back to the family's own page-off, which copies a
whole surface from offset 0.

Whether the family really works per plane and which validity bit it reads for plane 1 cannot be read from its binary.
The plugin decides it on the card: a process uses plane VRAM only after a self-test on a private 128 x 64 NV12 surface
has passed in that process (the GPU writes each plane, the CPU locks check each plane and the bytes around it, and a
CPU write is read back by the GPU). Until that verdict, and for good if it fails or the kernel does not offer the
grants, two-plane surfaces stay private images exactly as in 2.9. `debug.nvaccel_surfvram_ranged_shared`,
`debug.nvaccel_surfvram_ranged_validbit` and `debug.nvaccel_surf_plane_validbits` record what the kernel saw.

Preconditions, each checked while the driver runs: the accelerator offers plane grants (`NVAccelSurfPlanes` = 1 and
`debug.nvaccel_surf_planes` = 1; boot argument `nvaccel_surf_planes=0` turns them off), and the page-off wait without
the accelerator lock is on (`debug.nvaccel_pageoff_unlocked_wait` = 1). Behind a DMA mapper (VT-d) plane grants are
refused until the shared staging buffer has been mapped by a single-plane page-off (counted in
`debug.nvaccel_surfvram_ranged_off`); after that a plane's page-off maps a buffer of its own if it needs one. When the
unlocked page-off wait stands down for the boot, grants already made stay and new ones are refused.

What the plugin and the kernel say, and what a tester checks, is in
[TESTING-ON-HARDWARE.md](TESTING-ON-HARDWARE.md), "Two-plane surfaces".

## #476: deferred imported-surface uploads

### What the change is
An upload of a locked IOSurface's pages into a GPU image (`nvmtl_vk_image_write_host`) submits a copy and waits for its
fence before returning, so the caller can release the surface lock. The change returns before the fence completes. A lease keeps
the page import and the surface lock alive, a bounded queue holds the pending uploads, and a timer retires them as their
fences signal.

### What it needs
1. A pending-upload record: image, lease on the page import, in-flight submission, fence, surface lock to release.
2. A bounded queue. At the bound, the next upload waits for the oldest (never drops it).
3. The retire step releases, in order: the in-flight submission, the lease, then the surface lock (`IOSurfaceUnlock`).
   The unlock moves from `nvmtlSurfaceIn` to the retire path, which needs the surface reference kept alive until then.
4. Orderings that must hold:
   - GPU consumers of the image are ordered after the upload by the single queue, which is true while both use the one
     queue. Any second queue or an event wait breaks it.
   - A CPU readback (`nvmtlSurfaceOut`, `nvmtl_vk_image_read*`) of the same plane waits for the pending upload first.
   - Image destroy (`nvmtl_vk_image_destroy` frees at once) waits for the pending upload first.
   - A second upload to the same image waits for the first (per-image serialization).
   - Device loss (`nvmtl_vk_note_loss`): pending uploads complete as failed and release their locks.
5. The timer runs off every caller's thread and must not hold the accelerator lock or a surface lock while it waits.

### Hazards that make it opt-in
- The surface lock is held across frames. The app that owns the surface cannot lock it for CPU writes until the upload
  retires. A frame-rate app that writes its surface every frame may stall on the lock; the bound and the retire latency
  decide whether it does.
- The retire latency is bounded by the GPU, so a busy GPU lengthens the lock.
- A leak in the retire path leaks a surface lock, which hangs the owner.

## Harness runs that decide them

Run each on the test card with the four switches above off, then on, one at a time, and once more with
`nvaccel_surf_planes=0`. Keep the driver log and the kernel counters (`nvaccel_pageoff_*`, `nvaccel_surface_gpu_*`,
`nvaccel_surface_fence_*`, `nvaccel_surfvram_ranged*`, `nvrmfb_flip_*`) from each run. On RTX 50 note which decoder
produced the video frames ([TESTING-ON-HARDWARE.md](TESTING-ON-HARDWARE.md), "Video"): the decode service can now use the codec library's
decoder, whose frames are NV12 two-plane surfaces filled by the CPU like the built-in decoder's.

1. NV12 upload / GPU read-back / CPU page-off, 45 frames, planes written with distinct patterns: each plane comes back
   whole and only that plane changes; with `nvaccel_surf_planes=0` the same frames through private images.
2. Surface-order test, 1,100 frames: frames reach the CPU pages in submission order, none torn or repeated. Runs for both
   changes.
3. Imported-page upload with deferral, 120 frames: every deferred upload retires, the queue bound holds, the owner's lock
   latency (time from its `IOSurfaceLock` call to return) is measured per frame. Decides #476; fail it if the 99th
   percentile lock latency exceeds one frame at the panel's refresh rate.
4. Screen capture running (a recorder or Parsec encoder) with a 1080p Metal app: frames per second and `flip_us_sum /
   flip_n` with and without. The earlier cache work was observed to slow capture without the plane seed; this run covers
   that interaction.
5. Window drag at the panel's refresh rate with the capture running: WindowServer CPU per presented frame, and the count of
   imports (no log line counts them: `family VRAM import cache` is printed once per process and says only whether the
   cache is on).
6. A forced device loss during runs 2 and 3: every pending upload completes as failed, no surface stays locked.

## What would change the plan
- If run 1 or the plugin's self-test shows that the family keeps one set of validity words per surface (a non-zero
  `debug.nvaccel_surfvram_ranged_shared` with log lines `... plane 0 has the same resource, VRAM or validity words`),
  plane VRAM stays refused for those surfaces (the 2.9 path) and #475 needs a validity bit per plane in the kernel.
- If run 3's lock latency exceeds a frame, #476 should hold the surface lock only for the copy submission and keep a
  private snapshot of the pages for the deferred part. That costs a CPU copy and may cancel the gain.
